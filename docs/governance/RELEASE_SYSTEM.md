# Release System

The release system freezes one exact platform source tree and binds every published package to machine-readable verification evidence.

## Frozen truth

A release is represented by three repository-root documents:

- `RELEASE_MANIFEST.json` is the exact file inventory, size map, content digests, source-tree digest, Python requirement, and platform version.
- `RELEASE_EVIDENCE.json` records architecture, algorithm, concurrency, performance, and regression evidence for that exact manifest.
- `RELEASE_AUTHORITY.json` binds the manifest digest and evidence digest into the publication authority receipt.

These files are generated by the release subsystem. They are never maintained as a manual test-count or hand-edited release baseline.

## Generation order

1. Audit the current source tree, including the generic repository boundary, without treating a previous frozen manifest as current source truth.
2. Run architecture and governance quality checks over the same frozen source snapshot.
3. Run the machine-readable regression plan.
4. Rebuild the manifest and reject the operation if the source tree changed during verification.
5. Publish the new manifest, evidence, and authority receipt.
6. Run the final repository-boundary audit including the newly frozen release manifest.
7. Build and self-verify release packages.

## Verification commands

`python scripts/generate_release_evidence.py` generates the frozen release evidence set after the source tree is clean enough to qualify.

`python scripts/verify_release_evidence.py` verifies that the frozen release still matches the checkout and that all required evidence remains valid.

`python scripts/release_package.py` builds the governed release package.

`python scripts/verify_release_package.py <package>` independently verifies package membership and digests against the frozen release authority.

A historical release remains immutable evidence for its historical source tree. It must not be used as the current development truth after the source tree changes.

## Downstream projects

The upstream platform release contains only generic platform-owned files. Downstream projects, task definitions, concrete environment providers, model selections, deployment inventories, experiment outputs, and project-specific evidence belong to downstream repositories and must never appear in the upstream release manifest.
